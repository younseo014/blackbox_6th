# 3-camera single-person tracking: baseline and evaluation

## Why this document exists

Before the study runs, every tracking claim has to be re-runnable. This
describes the harness, the baseline it produced, what it deliberately does not
measure, and where each threshold came from.

Run it with:

```bash
npm run eval:tracking -- --model mediapipe-heavy
```

Outputs land in `docs/tracking-eval/<model>.json` and `<model>.md`. The process
exits non-zero if any pre-registered acceptance criterion fails.

## Data policy

Scenarios come from exactly two places:

- public datasets (COCO-WholeBody, OCHuman, WILDTRACK, CMU Panoptic / H3WB)
- developer-recorded pre-validation clips of empty rooms, chairs, hangers,
  mannequins, reflections, posters and lighting changes

Study participant recordings are never used for evaluation or for model
improvement. The built-in scenarios are synthetic and labelled
`synthetic:developer-pre-validation`; every scenario file must declare a
`source`, and the runner refuses one that does not.

In normal operation nothing changes: no video, audio or face features are
stored. Training-data collection stays behind a separate developer mode with
explicit consent.

## Architecture as it now stands

```
per camera:   PoseLandmarker -> selectLockedPose -> confirmPoseSelection
                                        |
                                 CameraObservation
                                        |
all cameras:              updateGlobalPersonTrack  <- one person, always
                                        |
                            GlobalPersonTrack { joints[], presence }
```

- `app/global-person-track.ts` - the single global owner. Three cameras produce
  at most one `GlobalPersonTrack`, and each joint carries `observed`,
  `inferred` or `missing`.
- `app/pose-scheduler.ts` - at most one body inference per animation frame,
  with per-camera cadence earned from what that camera is looking at.
- `app/pose-model-adapter.ts` - the seam where RTMW replaces MediaPipe.
- `app/tracking-eval.ts` + `app/tracking-eval-scenarios.ts` - the harness.

### Coordinate frames, stated honestly

There is no camera calibration yet, so there is no metric space to fuse into.
The fused skeleton lives in the **primary camera's normalized image frame**
(`GlobalPersonTrack.coordinateFrame`). Joints borrowed from another camera are
re-projected by a torso-anchored similarity transform, which is an
approximation, and are therefore always marked `inferred` - never `observed`.
`GlobalPersonTrack.calibrated` is hard-coded `false`; nothing in the UI or the
stored record presents these as true 3D coordinates.

`jointAnalysisWeight()` halves an inferred joint's weight relative to an
observed one, so downstream analysis cannot treat the two as equivalent.

## Threshold provenance

| Constant | Value | Why |
| --- | --- | --- |
| `MIN_JOINT_VISIBILITY` | 0.25 | Matches the visibility floor already used by `pose-target-lock.ts`, so the fusion layer does not disagree with the per-camera tracker about what "seen" means. |
| `GLOBAL_CONFIRMATION_FRAMES` | 3 | Same as the existing `POSE_CONFIRMATION_FRAMES`. Costs ~200-300ms of the 1s recognition budget and removes single-frame hallucinations. |
| `GLOBAL_RELEASE_AFTER_MS` | 2500 | Matches `RELEASE_AFTER_MS` in the per-camera lock, so the global layer never releases before the camera layer does. |
| `GLOBAL_COAST_MS` | 700 | Roughly one scheduler round plus a frame. Long enough to ride out a handoff, short enough that a departed person is not reported present for a second. |
| Continuity gate, 12 torso-lengths/sec | 12 | A fast walk at a 0.2-frame torso is ~2-3 torso lengths/sec; 12 leaves headroom for a close-up sprint while rejecting a jump to a different body. Verified by the `teleporting body` unit test. |
| Limb asymmetry floor, 0.25 | 0.25 | Perspective foreshortening routinely halves a limb; a 4x mismatch between paired limbs does not occur on a real body. Tuned against the `decoy-furniture` scenario. |
| `POSE_INTERVAL_MS.primary` | 100 | The 10 FPS top of the required 5-10 FPS body budget. |
| `POSE_INTERVAL_MS.idle` | 300 | Derived from the 1s recognition budget, not chosen for round numbers. Worst case a person enters just after an idle poll: 300ms to notice, then 2 x 200ms `alerted` frames to reach `GLOBAL_CONFIRMATION_FRAMES` = 700ms, leaving 300ms of margin. At 500ms idle the same path costs 900ms and has no margin. Asserted by a unit test. |
| `GLOBAL_OBSERVATION_TTL_MS` | 1000 | Two scheduler slots. A camera waiting its turn keeps contributing; one that has stopped seeing anything drops out. |

These are starting points, not settled values. Change one, re-run the harness,
and record the before/after in this file.

## Synthetic regression floor (MediaPipe Pose Heavy + global fusion)

Generated by `docs/tracking-eval/mediapipe-heavy.json`. All ten synthetic
scenarios pass all six pre-registered criteria. These prove the tracking layer
does not regress; they say nothing about real footage - see the section after.

| Scenario | Presence acc. | Retention | Handoffs | Worst handoff gap |
| --- | --- | --- | --- | --- |
| empty-room | 100.0% | n/a | 0 | - |
| decoy-furniture | 100.0% | n/a | 0 | - |
| entry-latency | 98.3% | 98.0% | 0 | - |
| side-view | 96.7% | 96.7% | 0 | - |
| back-view | 96.7% | 96.7% | 0 | - |
| headless | 96.7% | 96.7% | 0 | - |
| upper-body-only | 96.7% | 96.7% | 0 | - |
| distant-small | 96.7% | 96.7% | 0 | - |
| camera-handoff | 98.7% | 98.7% | 2 | 100 ms |
| three-camera-overlap | 98.0% | 98.0% | 0 | - |

The sub-100% presence figures are entirely the 2-frame confirmation delay at
the start of each scenario; that is the intended trade for zero false
positives, and it stays inside the 1s recognition budget.

**One real defect was found and fixed by this harness**: a pure side view, where
only one shoulder and one hip are visible, previously produced no torso anchor
at all and therefore no track. `torsoFrame()` now resolves a single
shoulder-hip pair and reports `facingFront: null`, so an unknown facing can
never mirror the skeleton left-for-right.

## Real-data results (COCO-WholeBody val)

714 single-person and 375 people-free COCO val2017 images, each replayed as a
6-tick steady burst. Every model sees the **same images, the same EfficientDet
person box and the same scoring code** - only the pose backend differs.

Retention is measured after the confirmation ramp, because the gate cannot
report `present` during its first frames; acquisition speed is measured
separately by recognition latency.

| Condition | MediaPipe Heavy | RTMW-m 256x192 | RTMW-l 256x192 | RTMW-l 384x288 |
| --- | --- | --- | --- | --- |
| front | 85.7% | 88.8% | 91.9% | 90.8% |
| side | 60.0% | 40.0% | 60.0% | 60.0% |
| back | 75.0% | 83.9% | 85.7% | 85.7% |
| head_occluded | 54.2% | 87.5% | 83.3% | 83.3% |
| partial_body | 80.2% | 82.4% | 87.9% | 83.5% |
| distant | 31.3% | 65.1% | 60.2% | 62.7% |
| **overall retention** | 76.6% | 84.5% | **86.7%** | 85.7% |
| **visible-joint detection** | 69.5% | 84.7% | **86.3%** | 86.2% |
| mean joint error (normalized) | 0.0301 | 0.0211 | 0.0158 | **0.0152** |
| empty-frame false positives (375 people-free images) | 4 | 4 | 4 | **0** |
| ONNX Runtime CPU latency | n/a | **11.1 ms** | 30.9 ms | 58.7 ms |

Read plainly:

- **RTMW beats MediaPipe Heavy on every condition this study cares about.** The
  two largest gaps are exactly the two the capture setup will produce: a distant
  person (31% -> 60-65%) and a person whose head is not visible (54% -> 83-88%).
- **Only RTMW-l 384x288 reaches zero empty-frame false positives.** One of 375
  people-free images fools every other backend. That is the single criterion
  with the tightest budget (< 1 per camera per 12 h), so it outweighs
  RTMW-l 256x192's 1-point retention lead.
- **Side view is the one condition nothing fixes** and RTMW-m makes it worse
  (40%). The sample is small (5 images) so this is weak evidence, but it is the
  known weak spot: see the single shoulder-hip torso anchor below.
- **No configuration meets the acceptance targets yet.** Best retention is 86.7%
  against a 95% target; best visible-joint detection is 86.3% against 90%.

### Why the numbers are still short

Per-tick attribution (`npx tsx scripts/diagnose-eval.ts coco-wholebody-val`) on
the MediaPipe run:

| Cause | Share of person-present ticks |
| --- | --- |
| tracked correctly | 38.3% |
| in the confirmation ramp (not a failure) | 38.3% |
| **pose model returned nothing** | **17.9%** |
| no detector evidence | 3.5% |
| rejected by the anatomy check | 2.0% |

The bottleneck is the pose model finding nothing at all - 60% of distant and 46%
of head-occluded ticks - not any threshold in our tracking layer. Anatomy
rejection costs 2.0%, so loosening it cannot buy more than 2 points. **Switching
the backend is the change that moves these numbers; tuning our gates is not.**

One caveat on comparability: RTMW is top-down and only runs where EfficientDet
found a person, so its empty-frame advantage partly reflects that architecture
rather than the weights.

### RTMW visibility had to be calibrated

RTMW is a SimCC model. Its raw output is an unbounded classification peak, and
on COCO-WholeBody the peak for an **occluded** keypoint has a median of 2.60
against 4.04 for a visible one. Clamping that peak into [0,1] - the obvious
thing to do - destroys the distinction entirely and marks every occluded joint
as confidently seen, which would break the `observed` / `inferred` / `missing`
contract this whole design rests on.

`scripts/fit_rtmw_visibility.py` fits a 2-parameter logistic from the peak to
P(visible), trained and tested on disjoint **image** splits of COCO-WholeBody
val (splitting by keypoint would leak, since keypoints from one photo are
correlated). Coefficients live in `config/rtmw-visibility-calibration.json`.

| Backend | Held-out AUC | Precision @ 0.25 | Recall @ 0.25 |
| --- | --- | --- | --- |
| MediaPipe Heavy (native visibility head) | **0.889** | 0.939 | 0.901 |
| RTMW-l 256x192 (calibrated) | 0.814 | 0.844 | 0.992 |
| RTMW-l 384x288 (calibrated) | 0.805 | 0.827 | 0.998 |
| RTMW-m 256x192 (calibrated) | 0.800 | 0.822 | 0.998 |
| RTMW, uncalibrated | 0.500 | 0.786 | 1.000 |

So the trade is explicit: **RTMW localises better, MediaPipe knows better what
it cannot see.** If RTMW is adopted, its weaker occlusion awareness is a known
cost that the `inferred` weighting has to absorb.

## Detector-driven improvement (the biggest single lever)

The per-tick attribution said the pose model "returned nothing" on 17.9% of
person ticks. That turned out to be mostly a **detector** problem, not a pose
problem: RTMW is top-down, so a person EfficientDet-Lite0 misses is a person
RTMW never sees.

Measured on COCO-WholeBody val (714 single-person images, 2307 people-free),
`scripts/sweep_detectors.py`:

| Detector | thr | recall | tiny <15% | small 15-25% | empty FP (of 2307) | CPU ms |
| --- | --- | --- | --- | --- | --- | --- |
| EfficientDet-Lite0 (shipping) | 0.50 | 90.2% | 40.0% | 69.1% | 19 | 13.3 |
| EfficientDet-Lite0 | 0.35 | 93.4% | 60.0% | 77.9% | 55 | 13.3 |
| EfficientDet-Lite0 | 0.30 | 93.8% | 60.0% | 79.4% | 78 | 13.3 |
| YOLOX-tiny | 0.50 | 94.8% | 53.3% | 85.3% | 44 | 12.8 |
| YOLOX-m | 0.85 | 91.9% | 60.0% | 79.4% | 9 | 60.5 |
| YOLOX-m | 0.80 | 94.7% | 66.7% | 88.2% | 14 | 60.5 |
| YOLOX-m | 0.75 | 95.7% | 73.3% | 91.2% | 18 | 60.5 |

The shipping detector's 40% recall on subjects under 15% of frame height is the
hard ceiling on the "distant person" condition. It is a **threshold** effect as
much as a model one: the same model reaches 60% at 0.35.

YOLOX-m strictly dominates. At the same false-positive budget as
EfficientDet-Lite0 @0.50 (19 vs 18 on 2307 empty images) it recalls 95.7%
against 90.2%, and 73.3% of tiny subjects against 40.0%.

Cost: 60.5 ms against 13.3 ms on CPU. The detector runs on the slow cadence
(`DETECTOR_INTERVAL_MS`, 400-1200 ms per camera), not per frame, so at the
tracking cadence three cameras cost ~150 ms/s of one core - affordable, and
expected to improve under WebGPU.

## End-to-end results: every configuration through the full tracker

Same 714 person + 2400 people-free images, same scoring code, RTMW-l 384x288
unless stated.

| Configuration | retention | visible-joint detection | empty FP | distant | head-occluded |
| --- | --- | --- | --- | --- | --- |
| **MediaPipe + EfficientDet@0.50 (shipping)** | **78.3%** | **71.3%** | **20** | 32.5% | 54.2% |
| MediaPipe + EfficientDet@0.35 | 80.4% | 73.0% | 48 | 34.9% | 54.2% |
| RTMW-l384 + EfficientDet@0.50 | 90.8% | 91.3% | 48 | 68.7% | 91.7% |
| RTMW-l384 + EfficientDet@0.35 | 94.7% | 95.0% | 136 | 80.7% | 95.8% |
| RTMW-l384 + EfficientDet@0.30 | 95.5% | 95.8% | 192 | 83.1% | 100.0% |
| RTMW-l384 + YOLOX-tiny@0.50 | 95.9% | 95.8% | 140 | 81.9% | 87.5% |
| RTMW-l384 + YOLOX-m@0.85 | 91.7% | 92.5% | 32 | 75.9% | 91.7% |
| RTMW-l384 + YOLOX-m@0.80 | 94.7% | 95.2% | 52 | 85.5% | 95.8% |
| **RTMW-l384 + YOLOX-m@0.75 (recommended)** | **95.8%** | **96.1%** | 64 | **89.2%** | 95.8% |

**RTMW-l 384x288 + YOLOX-m @0.75 is the first configuration to meet both
quality targets** - 95.8% against a 95% retention target and 96.1% against a
90% visible-joint target - and it does so with fewer empty-frame false
positives than any EfficientDet configuration of comparable quality
(64 vs 192 at EfficientDet@0.30).

Against what ships today that is **+17.5 points of retention and +24.8 points
of joint detection**, with distant-person retention going 32.5% -> 89.2% and
head-occluded 54.2% -> 95.8%.

### The one number that is not yet trustworthy

The empty-frame false-positive column is a **relative ranking, not a
prediction**. COCO's people-free images are arbitrary web photographs - food,
landscapes, vehicles - not a fixed camera pointed at a static empty room. Two
things make the real figure different and neither can be measured here:

- The background gate. In the app, acquisition also requires recent foreground
  change; a still photograph has no such signal, so the converter leaves it at
  zero and lets the detector alone decide.
- Independence. A fixed camera sees nearly the same frame every time, so a
  false positive is not an independent draw - it will either never happen or
  happen continuously.

The acceptance budget (< 1 per camera per 12 h ~ 2.3e-6 per frame at 10 FPS)
cannot be verified with 2307 images at all; the finest resolution available
here is 4.3e-4. **Only the developer-recorded empty-store footage can settle
this**, and it does not exist yet.

## Threshold fitting on real data

`scripts/fit-tracking-thresholds.ts` sweeps `TrackingTuning` over a real
scenario, fitting on half the images and scoring on the other half.

The limb-asymmetry floor was the one finding worth acting on. It was set to
0.25 by reasoning about foreshortening; on real images that rejected genuine
bodies:

| limb asymmetry floor | RTMW retention | RTMW empty FP | MediaPipe retention |
| --- | --- | --- | --- |
| 0.25 (old) | 85.7% | 0 | 76.6% |
| 0.15 | 89.8% | 0 | 78.3% |
| **0.10 (fitted)** | **90.6%** | **0** | **78.3%** |
| 0.05 | 91.0% | 4 | 78.4% |
| 0 (gate disabled) | 91.3% | 4 | 78.6% |

0.10 is the knee: it recovers 4.9 points of retention for free, and 0.05 starts
letting empty-frame false positives through. **`DEFAULT_TUNING.limbAsymmetryFloor`
is now 0.1**, held-out gain +4.76 points with zero added false positives.

`minJointVisibility` and `confirmationFrames` were left alone: the sweep shows
no held-out gain from moving them, and still images cannot speak to the
confirmation count at all, since its whole job is to reject single-frame
hallucinations in video.

## What this harness does not measure

Stating these plainly rather than implying coverage:

- **Pose model inference cost.** The replay harness runs in Node against
  recorded landmarks; it measures the fusion layer only (0.003-0.02 ms/tick).
  Model A/B numbers must come from a browser benchmark.
- **GPU utilisation and browser process memory.** Not reachable from Node.
- **CCTV-like footage.** COCO is web photography, not a fixed overhead camera in
  a shop. The WILDTRACK download exists to close this gap and is not yet scored.
- **Multi-camera behaviour on real data.** Every real scenario so far is single
  camera, so handoff and cross-camera joint fusion are still only covered by the
  synthetic set.
- **Browser inference cost.** The latency column above is ONNX Runtime on CPU.
  WebGPU in the browser will differ and must be measured before a backend is
  chosen for the study.
- **12-hour behaviour.** The `*Per12h` figures are linear extrapolations from
  scenario duration. A real soak run has not been performed.
